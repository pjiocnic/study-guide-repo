## High-Cardinality Mitigation Example: `"ZIP Code"`

### **Before (Naïve One-Hot Encoding)**

```
ZIP Code: 94105 → 50,000 one-hot columns (ZIP_00001, ZIP_00002, … ZIP_50000)
Most columns are 0 for each row → Sparse Matrix
↑
Memory usage & training time spike
↑
Model overfits to rare ZIP codes
```

**Visual:**

```
[ 0, 0, 0, ..., 1, ..., 0 ]   ← 50,000 columns!
```

---

### **After (Mitigation Strategies)**

#### **1. Frequency Encoding**

Replace each ZIP code with how often it appears in the dataset.

```
ZIP Code → Frequency
94105 → 1,240
10001 → 980
02139 → 560
```

Result: **1 numeric column instead of 50,000**.

---

#### **2. Target Encoding**

Replace each ZIP code with the average target value for that ZIP.
*(For regression/classification tasks, use training folds to avoid leakage)*

```
ZIP Code → Avg Target
94105 → 0.82
10001 → 0.57
02139 → 0.44
```

Result: **1 numeric column** capturing predictive power.

---

#### **3. Clustering / Grouping**

Map ZIPs into broader regions (e.g., first 2–3 digits only):

```
ZIP Code → Region
94105 → Region 94
94043 → Region 94
02139 → Region 02
```

Result: **few categories → fewer one-hot columns**.

---

#### **4. Hashing Trick**

Hash ZIP codes into a fixed number of buckets (e.g., 100):

```
94105 → Bucket 42
10001 → Bucket 8
02139 → Bucket 77
```

Result: **fixed-size encoded feature regardless of cardinality**.

---

### **Impact Summary Table**

| Approach            | Final Features    | Pros                     | Cons                     |
| ------------------- | ----------------- | ------------------------ | ------------------------ |
| One-hot (naïve)     | 50,000            | No info loss             | Huge memory use, overfit |
| Frequency encoding  | 1                 | Simple, low memory       | Loses category meaning   |
| Target encoding     | 1                 | Captures target relation | Risk of leakage          |
| Clustering/grouping | Few (5–50)        | Retains geography info   | May lose fine detail     |
| Hashing trick       | Fixed (e.g., 100) | Scales well              | Hash collisions possible |

Yes — there are a few **practical rules of thumb** you can follow when deciding how to mitigate high cardinality. These work as a quick checklist before you jump into complex feature engineering:

---

## **Rule of Thumb for High-Cardinality Features**

### 1. **Check Proportion of Unique Values**

* If **unique values > 5–10% of dataset size**, treat as *potential high cardinality*.
* Example: 10,000 rows and 2,000 unique ZIP codes → 20% → high risk.

---

### 2. **Check Category Frequency Distribution**

* If many categories occur **very rarely** (e.g., <1% of rows each), they’re likely noise.
* Group rare categories into `"Other"` unless domain knowledge says they’re important.

---

### 3. **Match Encoding to Model Type**

| Model Type      | Preferred Strategy                                 |
| --------------- | -------------------------------------------------- |
| Linear/Logistic | Frequency encoding, target encoding, hashing trick |
| Tree-based      | Target encoding, grouping rare categories          |
| Deep Learning   | Learn embeddings for categorical variables         |

---

### 4. **Preserve Predictive Signal, Drop the Rest**

* Before encoding, check the **relationship with target** (e.g., Chi-squared for classification, ANOVA for regression).
* If the variable shows **no correlation**, consider dropping it instead of spending effort encoding it.

---

### 5. **Ensure Train–Test Consistency**

* Always check that all important categories appear in both train and test sets.
* Use **stratified splitting** for categorical variables when possible.

---

### 6. **Control Model Complexity**

* For tree-based models: increase `min_samples_leaf` or `min_child_weight` to avoid overfitting rare categories.
* For linear models: use regularization (L1/L2) after encoding to prevent noise features from dominating.

---

💡 **Quick Mnemonic:** **C.A.R.D.**

1. **C**heck uniqueness ratio
2. **A**ggregate rare categories
3. **R**egularize or choose encoding based on model type
4. **D**istribute categories evenly in train/test
